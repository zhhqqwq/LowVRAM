# Runtime Adapter — P1-05

P1-05 defines the process-execution boundary between LowVRAM and external model runtimes.

## Rebaseline acceptance contract

Under the restarted P1 sequence, P1-05 must provide:

- a runtime abstraction rather than llama.cpp-specific process code;
- deterministic argv construction;
- shell-free process startup;
- stdout and stderr capture;
- exit-code handling;
- timeout handling;
- `runtime_not_found` classification for unavailable executables;
- `process_crash` classification for non-zero runtime exits;
- structured execution results;
- process-tree cleanup after timeout;
- behavior that does not depend on shell quoting on Windows or Linux.

## Public interface

```python
from lowvram.models import RuntimeExecutionRequest
from lowvram.runtime import LlamaCppRuntimeAdapter

adapter = LlamaCppRuntimeAdapter()
request = RuntimeExecutionRequest(
    executable="/path/to/llama-cli",
    arguments=["--version"],
    timeout_seconds=10,
)

result = adapter.execute(request)
```

`RuntimeAdapter` defines:

- `build_command(request) -> list[str]`
- `execute(request) -> RuntimeExecutionResult`

`SubprocessRuntimeAdapter` owns generic local-process execution.
`LlamaCppRuntimeAdapter` only supplies the stable runtime name `llama.cpp`.

## Command boundary

The execution source of truth is argv:

```text
[executable, argument_1, argument_2, ...]
```

The adapter invokes `subprocess.Popen(..., shell=False)`. A path or argument containing
spaces, semicolons, command substitutions, or other shell syntax remains one argv item and is
not reinterpreted by a shell.

The same argv contract is used on Windows and POSIX. Native Windows process behavior still
requires native Windows CI or real-system validation; the current repository CI runs on
Ubuntu.

## Structured execution result

Every execution records:

- runtime name;
- success/failure;
- exit code when the runtime itself exits;
- stdout;
- stderr;
- elapsed seconds;
- normalized error type;
- error message.

Success requires exit code 0 and no error fields.

A non-zero runtime exit is `process_crash` and preserves the real exit code.

A timeout is `timeout` and intentionally reports `exit_code = null` because any later
termination code is generated by LowVRAM cleanup, not by the runtime itself.

## Process-start classification

P1-05 distinguishes an unavailable/unusable executable from unrelated operating-system
resource failures.

The following are classified as `runtime_not_found` / runtime unavailable:

- missing file/path;
- permission denied;
- executable format not runnable by the OS.

Other startup `OSError` values, such as file-descriptor/resource exhaustion, are
`unknown` rather than falsely claiming the runtime is missing.

This classification uses portable errno values plus common Windows executable-start error
codes.

## Timeout cleanup

On timeout:

1. LowVRAM asks psutil for the direct process and recursive descendants.
2. Descendants and then the root receive terminate.
3. Survivors after a bounded wait receive kill.
4. The direct `Popen` root also receives a kill fallback if it is still alive after psutil
   cleanup.

The direct-root fallback prevents a psutil lookup failure from turning a timeout into an
unbounded wait on the runtime process.

Process-tree cleanup is best effort. Native Windows and real descendant edge cases should
also be exercised by platform integration tests before the final P1 Runner Gate.

## Scope boundary

P1-05 does not search for llama.cpp, translate Recipe fields, add the Standard Prompt, parse
performance output, or construct Benchmark records.

P1-06 owns executable discovery/version probing.

After this rebaseline passes, P1-06 is the next active Gate.
